# AUDIT.md — журнал аудита

Этот файл фиксирует реальные архитектурные проблемы, найденные в проекте, и то, как они были устранены. Комментарии в коде (`diabetes.yaml`, `regex_parser.py` и др.) ссылались на этот файл до того, как он был создан — теперь он на месте.

**Методология:** каждая находка ниже проверялась исполнением реального кода — юнит-тестами на реальных классах, полным end-to-end через `FastAPI TestClient` с настоящей авторизацией, либо прямым запуском через `version_manager.hot_reload()` на всей базе знаний. Ни один пункт не отмечен как решённый только на основании чтения диффа.

---

## 1. 219 из 243 файлов правил не загружались

**Симптом:** `RuleVersion.from_yaml()` понимал только схему `conditions: [...]`, а 219 файлов (90% базы знаний) были написаны в схеме `thresholds:`/`condition: any`. Загрузчик не падал — молча создавал правило с пустым списком условий, которое никогда не срабатывало.

**Проверка:** прогон `version_manager.hot_reload()` по всем 243 файлам показал 24 живых / 219 мёртвых.

**Решение:** `RuleVersion.from_yaml()` научили распознавать оба формата — старый конвертируется на лету через `_convert_old_format()`. Итог: 243/243 живых.

## 2. id-коллизия при декомпозиции многопараметровых правил

**Симптом:** при конвертации файла с несколькими параметрами (например, `acute_coronary_syndrome.yaml` — тропонин I, тропонин T, КФК-МВ) все условия получали один и тот же `id` — файла целиком. Три разных находки в отчёте выглядели как три одинаковые строки.

**Проверка:** пациент с одновременно повышенными тремя кардиомаркерами — до фикса 3 находки с одинаковым `id`, после — 3 разных.

**Решение:** каждому условию присваивается `id = "{top_id}_{parameter}"`, если параметров больше одного; при одном параметре — `id = top_id` (сохраняет связь с `clinical_interpretations.yaml`/`diagnosis_labels`).

## 3. `PostProcessor._apply_exclusions` не матчил id

**Симптом:** та же путаница id правила/условия. Пациент с eGFR=10 (стадия 5 ХБП) получал 25 диагнозов одновременно, включая явно противоречащий `ckd_stage3` — хотя правило исключения (`if: ckd_stage5, then: [ckd_stage4, ckd_stage3, ...]`) для этого случая уже существовало в `clinical_logic.yaml`.

**Решение:** `_apply_exclusions` теперь матчит и по id правила, и по id отдельного условия (`ckd_stage5_egfr` эквивалентен `ckd_stage5`). Тот же сценарий после фикса: 23 диагноза (правило исключения отработало для сконфигурированных пар).

## 4. `ConflictResolver` — та же проблема id, плюс отсутствие дедупликации

**Симптом:** идентичная путаница `finding.id` vs `rule.rule_id`, из-за которой ни `conflicts_with`, ни `priority` не работали ни для одного правила с собственным id условия (то есть для всех enriched-подобных многоусловных файлов).

**Проверка:** синтетический сценарий диабет (`priority: CRITICAL`, `conflicts_with: [prediabetes]`) vs преддиабет (`priority: LOW`) — до фикса оба диагноза оставались в отчёте, после — преддиабет корректно вытесняется.

**Решение:** резолвер восстанавливает связь `finding.id → rule_id` через реальный список условий каждого правила, дедуплицирует результат по id.

## 5. `NameError` в `analysis_pipeline.py`

**Симптом:** ветка cache-hit создавала `ClinicalFinding`/`Recommendation` без соответствующих импортов. Не крашило приложение — исключение перехватывалось широким `except Exception`, кэш молча переставал работать при каждом попадании.

**Решение:** добавлены недостающие импорты. Покрыто регрессионным тестом `tests/integration/test_cache.py`.

## 6. Шум от многопараметровых нефрологических файлов

**Симптом:** ~50 файлов в `nephrology/` независимо используют один и тот же грубый порог по eGFR — один повышенный креатинин выдавал 20+ равноправных диагнозов (от контраст-нефропатии до синдрома Гудпасчера) без дифдиагностической ценности.

**Решение:** `PostProcessor._group_low_specificity_by_parameter` — если 3+ находки в отчёте делят один лабораторный параметр, они схлопываются в одну запись вида «23 возможных причины, требуется дифдиагностика», полный список сохраняется в `description`, ничего не теряется.

## 7. Дублирующийся контент: `diabetes.yaml` vs `glucose_ranges.yaml`

**Симптом:** два независимых файла описывали диагностику диабета 2 типа под разными id (`diabetes_glucose` и `diabetes_mellitus_type_2`) — пациент с glucose=8.0 получал два диагноза вместо одного.

**Решение:** критерии разделены между файлами (glucose → `glucose_ranges.yaml`, HbA1c → `diabetes.yaml`), оба используют общий `id: diabetes_mellitus_type_2`. Проверено тремя сценариями (только глюкоза / только HbA1c / оба) — дублей нет.

## 8. `RegexParser` — два жадных regex на строку

**Симптом:** ломался на составных именах параметров с цифрами (`HbA1c`, `T4 свободный`), запятой как десятичным разделителем, референсных интервалах в скобках, нескольких параметрах в одной строке.

**Решение:** переписан на токенизирующий парсер с явным разрешением неоднозначностей (значение — последний числовой токен в сегменте, а не первый). Проверено на всех перечисленных проблемных случаях.

## 9. `medical_data.json` отсутствовал

**Симптом:** `MedicalReferenceLoader` тихо деградировал до пустого справочника — 3 из 93 текстовых шаблонов интерпретации (`c_peptide`, `ferritin`, `mcv`) выводили пустую строку вместо клинического текста.

**Решение:** создан `knowledge/configs/medical_data.json` для 6 параметров, реально используемых в `comment_template`. Значения синхронизированы с `clinical_thresholds.yaml`, чтобы не плодить второй, расходящийся источник истины.

## 10. `SECRET_KEY` по умолчанию

**Симптом:** захардкоженное значение `"your-secret-key-change-me"`.

**Решение:** генерируется случайно при старте (`secrets.token_urlsafe(32)`), если не задан явно в `.env`.

## 11. Дефолтные пароли `admin`/`admin`, `doctor`/`doctor`

**Симптом:** захардкоженные пароли у ролей с полным доступом.

**Решение:** случайная генерация (`secrets.token_urlsafe(12)`) при первом запуске, пароль печатается в лог один раз и нигде не хранится в открытом виде. Проверено прямым HTTP-запросом на `/token` — `admin/admin` возвращает `401`.
